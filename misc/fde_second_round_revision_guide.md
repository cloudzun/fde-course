## 二、第 5-8 章与 Palantir 四阶段的严格对齐方案

### 对齐的核心原则

教材的 Discovery → Prototype → Build → Scale 与 Palantir 官方有**两套不同的阶段体系**，必须在每一章开头做显式映射，让读者清楚「教材在说什么、Palantir 官方在说什么、两者如何对应」。

### Palantir 官方体系全景对照（建议放入第5章 How 总纲）

```markdown
### 三套阶段体系的完整对照

| 本教材四阶段 | Palantir 用例生命周期 | Palantir Foundry 采纳四阶段 | Palantir AIP Activate | 阶段核心动作 |
|---|---|---|---|---|
| **Discovery** | Distilling functional requirements | Phase 1: Focus on use cases | Identify & Prioritize | 找对问题 |
| **Prototype** | Solution Design | Phase 2: Build infrastructure | Prototype & Validate | 快速证明 |
| **Build** | Sequencing development | Phase 3: Self-service growth | Deploy & Operationalize | 做实做稳 |
| **Scale** | （贯穿各阶段） | Phase 4: Hypergrowth | Scale & Transform | 放大复制 |

> **三套体系的粒度差异**：
> - 本教材四阶段：面向**单个项目的从0到1交付**，适合一线操作
> - 用例生命周期：面向**单个用例的需求→设计→开发**，适合技术执行
> - Foundry 采纳四阶段：面向**客户组织层面的平台成熟度**，适合高管决策
> - AIP Activate：面向**AI 能力的渐进式引入**，适合 AI FDE
```

**当前状态**：已从 6KB 扩写到 11KB，但仍是四章中**最需要加强的**。

**需补充的核心内容**：

**6.x 新增：与 Palantir Solution Design 阶段的对齐**

Palantir 的 Solution Design 阶段包含三个教材尚未充分覆盖的关键环节：

```markdown
### 6.x Ontology Design 深化：从草图到可运行的业务模型

#### 1. Object Type 设计原则（对标 Palantir Ontology 最佳实践）
Palantir 官方文档对 Ontology 有一句核心定义：
> "the Ontology serves as a digital twin of the organization, 
> containing both the semantic elements (objects, properties, links) 
> and kinetic elements (actions, functions, dynamic security)"

这意味着 Ontology 不只是"数据模型"，而是"可操作的业务数字孪生"。
原型期的 Ontology 设计应遵循：

| 设计原则 | 说明 | 反面模式 |
|---|---|---|
| **业务语言优先** | Object Type 命名用业务术语（"订单"而非"t_order"） | 照搬数据库表名 |
| **关系即业务逻辑** | Link Type 表达业务规则（"供应商-供应→零件"） | 只建外键关联 |
| **Action 即决策** | 设计可写回的 Action（"调拨建议→执行"） | 只做只读展示 |
| **先窄后宽** | 先建核心 3-5 个 Object Type，验证后再扩 | 一上来建 50 个 |

#### 2. 数据管道的"可演进架构"
原型管道要满足"今天能跑、明天能改、后天能进生产"。关键：
- 数据源接入用**配置驱动**（而非硬编码），便于 Build 阶段替换
- 转换逻辑用**可测试的函数**封装，而非散落在 notebook 里
- 留出**增量 vs 全量**的切换点（原型跑全量，生产必须增量）

#### 3. 原型的"可信度阶梯"
不是所有原型都需要同等精度。按可信度递进：
Level 1: 静态数据 + 手动刷新 → 够用于首次 Demo
Level 2: 自动刷新 + 真实近期数据 → 够用于高管决策 Demo
Level 3: 实时/准实时 + 完整业务闭环 → 够用于 Gate 通过进 Build
```

**6.x 新增：原型期的客户期望管理**

```markdown
### 6.x 原型期的客户期望管理：防止"原型=上线"的致命误解

**问题**：客户看到能跑的原型后，常见反应是"这不就行了吗，
为什么还要花 3 个月做 Build？"——如果管理不好预期，
要么被逼仓促上线（系统必崩），要么客户拒绝为 Build 付费。

**应对策略（Demo 时就要埋的三颗种子）**：
1. **Demo 时故意展示一个"原型能看到问题但解决不了"的环节**
   —— 比如："您看，这里显示了断供风险，但目前还不能自动
   生成调拨方案——这就是 Build 阶段要解决的"
2. **用安全和合规做挡箭牌**："原型跑在沙箱里，要进生产
   必须过安全审计——这需要 Build 阶段完成"
3. **量化 Build 的增量价值**："原型能覆盖 1 个场景，
   Build 能覆盖 5 个，ROI 是 X 倍"
```

### 第 7 章 Build 的对齐扩写

**当前状态**：已从 5KB 扩写到 11KB，方向对但缺少与 Palantir 的对齐。

**需补充**：

```markdown
### 7.x 与 Palantir Sequencing Development 的对齐

Palantir 在 Build 阶段的官方方法论强调"开发排序"——
不是把所有需求一起做，而是按"用户价值递减"排序交付：

**排序原则（RICE 变体）**：
| 因素 | 权重 | 说明 |
|---|---|---|
| Reach（触达面）| 高 | 多少用户每天会用到这个功能 |
| Impact（影响度）| 高 | 对核心 KPI 的改善幅度 |
| Confidence（可信度）| 中 | 我们对以上估计有多确定 |
| Effort（工作量）| 中 | 需要多少人天 |

**排序后的交付节奏**：
- 第 1-2 周：核心数据管道 + 最高 Reach 的功能
- 第 3-4 周：权限体系 + 数据质量规则
- 第 5-6 周：次要功能 + 培训
- 第 7-8 周：回注识别 + Gate 准备

### 7.x 生产化的"可运营移交"标准
Build 的终极产出不是"系统能跑"，而是"FDE撤场后系统还能跑"：
- 运维手册（而非只有开发文档）
- 值班 SOP（谁在什么时候看什么指标、出了什么问题找谁）
- 数据管道的健康度看板（客户自己能看到"昨晚的管道跑成功了吗"）
```

## 三、第 15 章 FDE × AI Agent 的高质量扩写方案

### 当前问题诊断

第 15 章目前 7.3KB / 72 行，作为全书的「落地抓手」章节**严重偏薄**。核心问题：
1. **缺少与 Palantir AIP 的具体对标**——AIP Logic、Automate、Agent Builder 均未展开
2. **缺少可落地的技术架构参考**——读者看完不知道"第一步该干什么"
3. **缺少中国市场的本土化指导**——信创环境下的模型选择、私有化部署
4. **缺少成熟度评估模型**——企业不知道自己"准备好了没有"

### 建议扩写到 20KB+ / 约 250 行，增加以下模块：

```markdown
### 15.x 对标 Palantir AIP：从工具到方法论

Palantir 的 AI 能力不是"在产品里加个 ChatGPT"，
而是一套完整的企业 AI 落地架构：

| Palantir AIP 组件 | 功能 | FDE 使用方式 | 中国替代方案 |
|---|---|---|---|
| **AIP Logic** | 编排 LLM + 业务逻辑的工作流 | 把重复的集成/转换做成 Agent | Dify / Coze / 自研编排引擎 |
| **AIP Automate** | 自动化执行动作（含写回） | Build 后的运维自动化 | n8n / Apache Airflow + LLM |
| **Agent Builder** | 为业务用户构建自助 Agent | Scale 阶段赋能客户自运营 | 通义千问 Agent / 豆包 Agent |
| **Ontology + AI** | AI 基于结构化本体推理 | 保证 AI 输出可溯源、可审计 | 知识图谱 + RAG |

### 15.x AI FDE 的技术栈参考（中国本土版）

**核心工具链（分层）**：

| 层级 | 推荐工具 | 说明 |
|---|---|---|
| 大模型底座 | 通义千问 / DeepSeek / GLM | 私有化可部署，信创兼容 |
| Agent 编排 | Dify（开源） / Coze（字节） | 低代码 Agent 搭建 |
| RAG 引擎 | LlamaIndex / 自研 | 企业知识库检索 |
| 向量数据库 | Milvus（开源、国产） | 信创友好 |
| Eval 评测 | Ragas / 自研评测集 | AI 输出质量保障 |
| 前端交互 | Streamlit / Gradio | 快速 AI 原型前端 |

### 15.x AI 赋能四阶段的具体落地 SOP

**SOP 9: AI FDE 四阶段落地清单**

| 阶段 | AI 赋能动作 | 工具/方法 | 产出物 | 风险等级 |
|---|---|---|---|---|
| Discovery | 访谈转写+痛点聚类 | Whisper+LLM | 结构化痛点报告 | 低 |
| Discovery | 制度文档速读 | RAG | 业务规则知识库 | 低 |
| Prototype | AI 辅助写代码 | Cursor/Copilot | 原型代码 | 低 |
| Prototype | Agent 化 Demo | Dify+AIP Logic | 可交互的智能体 | 中 |
| Build | 数据质量AI监控 | 异常检测模型 | 自动质量报告 | 中 |
| Build | LLM生成代码的审查 | 人工Review+测试 | 通过审查的代码 | 中 |
| Scale | 自助分析Copilot | RAG+Ontology | 用户可用的查询助手 | 高 |
| Scale | Agent化运维 | Automate工作流 | 自动化运维链路 | 高 |

### 15.x AI FDE 成熟度评估模型

**五级成熟度阶梯**（企业可自评当前所处级别）：

| 级别 | 名称 | 特征 | 进入条件 |
|---|---|---|---|
| L0 | 未启动 | FDE 团队未使用任何 AI 工具 | - |
| L1 | 个人提效 | 个别FDE用Copilot写代码、用LLM整理文档 | 无需组织级投入 |
| L2 | 流程嵌入 | AI 工具正式写入交付 SOP（如访谈必须用AI转写） | 需工具链统一、安全评审 |
| L3 | Agent 交付 | 交付物中包含 Agent/工作流组件 | 需 RAG+编排平台、Eval 体系 |
| L4 | AI 原生 FDE | AI 是交付主力，FDE 主要做编排/把关/业务判断 | 需成熟 Ontology + 完整 AI 平台 |

### 15.x 中国市场 AI FDE 落地的特殊考量

1. **模型私有化部署**：政企客户数据不出域，必须本地部署开源模型
   - 推荐：DeepSeek（高性价比）/ 通义千问（阿里生态）/ GLM（清华系）
   - 硬件：至少 A100×2 或等效国产 GPU（昇腾 910B）
   
2. **信创兼容**：AI 工具链需验证在国产 OS（麒麟/统信）+ 
   国产 CPU（鲲鹏/飞腾）上可运行
   
3. **合规红线**：
   - PIPL：AI 处理个人信息需单独同意
   - 生成式AI管理办法：面向公众的AI服务需备案
   - 算法推荐管理规定：推荐类AI需算法备案
   
4. **与现有平台的集成**：不要另起炉灶，AI 能力应作为
   "叠加层"集成到已有的数据平台/Ontology 之上
```

## 四、中国区成功案例的筛选标准与分析方法

### 案例筛选的四维框架

```markdown
### 案例筛选矩阵（四维评分，满分 20 分，≥14 分可入选）

| 维度 | 权重 | 评分标准（1-5分） |
|---|---|---|
| **FDE 方法论体现度** | 30% | 是否体现了"现场定制→平台回注"的完整闭环？仅是标品部署得 1 分，完整飞轮得 5 分 |
```
