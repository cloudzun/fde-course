## 1. 2.2 汇报线转型过渡方案（第3章）（⏳ 待确认）

**问题**：第3章 3.3 只给了方向（产品 > 工程 > 销售），缺过渡路径。

**我的研究与建议**：结合第13章中国云厂商实况（阿里 TAM 挂靠在客户成功/事业部、华为铁三角由"客户经理/解决方案/交付"三方制衡、腾讯 OTSS 挂靠事业群），中国企业几乎不存在"一步切换到产品线"的可能。建议在第3章 3.3 末尾增加「汇报线转型过渡方案」，采用三阶段渐进路径（按交接小结中指南原文）：
- **阶段1（6–12月）双线汇报**：行政归属不变，技术路线/能力回注/平台需求由产品线 dotted-line 管理，设产品+原部门联合评审会；
- **阶段2（12–24月）虚拟独立**：FDE 成为独立虚拟组织，绩效由产品线主导，销售/项目部仅保留商务对接权；
- **阶段3（24月+）正式独立**：划归产品/研发体系，完成组织归属调整。

**落地**：在第3章新增小节（如 3.3.1，不重编号、用子编号），并注明"参考华为铁三角与阿里 TAM 的组织演进经验"。

## 2. 2.3 招聘市场与薪酬竞争力（第12章）（⏳ 待确认）

**问题**：12.1 有面试题，但缺薪酬与人才来源。

**我的研究（2026 年市场公开数据）**：
- 交付/实施类工程师（传统交付岗）：月薪约 **12–21K**（2 年经验，如云计算技术支持岗）；
- 华为云 Stack 交付工程师：**15–18K·13 薪**；
- 阿里云业务架构师（政务方向，类 FDE 复合岗）：**20–50K·13 薪**；
- 云交付研发工程师（火山引擎等）：整体上移一档。

**结论**：FDE 若按"实施工程师"定价（12–18K）必招不到复合型人才；应**对标后端高级工程师 / 云业务架构师档（20K 起，资深 30–50K）**。

**建议落地（第12章 12.1 后新增 12.x「招聘市场与薪酬」）**：
1. **人才来源**：互联网大厂后端/全栈工程师转型（主力）、前咨询顾问转技术、行业 ISV 资深实施升维；
2. **薪酬基准**：对标后端高级工程师而非实施工程师；给"基础薪酬 + 项目回注贡献奖金"结构，避免纯人天计费心态（呼应 1.3）；
3. **双通道晋升**：技术专家线（FDE → 资深 FDE → 首席 FDE / 平台架构师）与管理线（FDE → 交付负责人 → 事业部负责人），两条线同级别同待遇；
4. **留存机制**：项目分红 / 股权（对标 Palantir 期权激励）、客户轮换防倦怠（12.2 已有基础）、知识署名（Playbook 作者署名）增强成就感。

## 3. 4.2 度量指标体系（第9章 9.5）（⏳ 待确认）

**问题**：9.5 已有教材自创四指标（回注率/复用率/交付效率/路线图影响力），新增行业指标怕两套打架。

**我的建议：并列增补，形成"两层指标体系"**（不建议推倒重写）：
- **第一层 · 平台飞轮健康度（9.5 现有四指标，保留）**：回答"能力有没有沉淀、有没有被复用"——这是 FDE 模式的**核心**，行业通用指标替代不了；
- **第二层 · 交付与客户成功（新增四个行业通用指标）**：
  - **TTFV（Time to First Value）**：合同签署 → 客户首次获得可量化价值的时间，衡量交付效率；
  - **Customer Health Score（客户健康度）**：活跃度 + 增购意向 + 关系质量综合评分；
  - **NPS / CSAT**：客户满意度基础指标；
  - **定制/平台代码比**：飞轮健康度的"最简单版"，目标是逐项目递减。
- **口径说明**：两层是"内因（飞轮）× 外果（客户）"的关系——飞轮转得好，TTFV 与健康度自然提升；第二层指标作为第一层的**结果验证**，不作为对一线 FDE 的单一考核（防止为了 TTFV 牺牲复用，与 1.3"卖能力"矛盾）。

**落地**：在 9.5 末尾新增「9.5.x 行业通用指标补充」小节，含上述口径说明与两层关系表。

## 4. 4.4 合规框架具体化（第14章 14.5）（⏳ 待确认）

**问题**：14.5 提到等保/信创/数据不出域，但缺可执行的检查清单与条文依据。

**我的研究（2026 年现行监管框架）**：核心对标文件包括《网络安全法》《数据安全法》《个人信息保护法（PIPL）》《网络安全等级保护 2.0（等保三级是政务/金融基线）》《信创产品安全测评规范（2026 版）》《数据分类分级安全规范》《政务信息系统安全运维规范》；国际场景另涉 ISO 27001 / SOC 2。信创适配范围：国产 CPU（鲲鹏/飞腾/龙芯）、国产 OS（麒麟/统信）、国产数据库与中间件。

**建议落地（第14章 14.5 后新增「合规检查清单」子节，或作为附录 H）**：
1. **等保 2.0**：按"定级 → 备案 → 建设整改 → 测评"四步；FDE 部署系统通常按**三级**基线（政务/金融），四步中 FDE 主要承担"建设整改"的技术侧；
2. **PIPL 红线**：AI/系统处理个人信息需单独同意；敏感个人信息（如医疗、金融）从严；数据不出域为硬约束；
3. **信创适配矩阵**：CPU/OS/数据库/中间件四层兼容性核对表（与 7.5 工具链验证、第16章 16.5 算力栈联动）；
4. **国际认证**：ISO 27001 / SOC 2 为出海或外企客户场景的加分项，建议标注"按客户要求裁剪"。
- 每项注明"**以最新监管口径为准**"，不逐字引用法条（教材定位为实操清单而非法律意见）。

## 5. 5.2 非 Palantir 案例（第4章）（⏳ 待确认）

**问题**：第4章五个案例全是 Palantir，缺中立性。

**我的研究与建议**：按指南四维框架（方法论体现度/可量化成果/可公开引用性/中国市场代表性），我们目前**没有可公开引用的一手来源、也没有内部项目可脱敏**（第一、二优先级均不可得）。因此建议采用**第三优先级方式**：
- 在第4章末尾新增一节「4.8 教学案例：两个脱敏综合案例（非 Palantir）」：
  1. **"某头部云厂商 × 制造业供应链"**：基于阿里云 DataWorks/华为云 DataArts 公开能力模型与教材四阶段框架，**综合提炼**的供应链协同案例；
  2. **"某城商行 × 数据中台（监管报送）"**：政务/金融场景综合案例；
- **明确标注**："本案例为基于多个真实项目与厂商公开案例综合提炼的教学案例，非特指某真实项目"——满足"明确标注虚构/提炼"的合规路径；
- 案例按指南**七段式模板**（背景→介入→技术方案→交付节奏→成果→回注→启示）撰写，成果指标标注"示意值"。
